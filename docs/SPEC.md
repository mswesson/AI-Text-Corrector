# TextCorrect — техническое задание на разработку

**Версия:** 4.0
**Дата:** 05.11.2026
**Тип документа:** функциональное и техническое ТЗ
**Статус:** готово для передачи в разработку
**Целевая платформа:** macOS 14 Sonoma и новее, Apple Silicon
**Технологический стек:** Swift, SwiftUI, AppKit
**Тип продукта:** Desktop Application / Menu Bar Utility
**Модель распространения:** бесплатный Open Source, GitHub
**Название:** TextCorrect — рабочее, может быть изменено перед релизом


## Актуальное уточнение поставки STT

По последнему решению пользователя ни одна STT-модель, включая Whisper Base, не входит в `.app`.
Whisper Base доступна в общем списке скачиваемых моделей. До установки модели диктовка предлагает
открыть каталог. После установки распознавание работает без интернета. Это уточнение имеет приоритет
над встречающимися ниже исходными требованиями о встроенной Base и диктовке сразу после установки.

## Актуальное уточнение Dock

По последнему уточнению пользователя приложение отображается в Dock как обычное Mac-приложение.
Иконка Menu Bar и работа после закрытия окна сохраняются; нажатие иконки Dock открывает настройки.

## Главный принцип реализации — лаконичность и понятность

При соблюдении функциональных требований и безопасности выбирать решение с наименьшим объёмом понятного кода.

- Использовать простые конструкции, короткие функции и понятные имена.
- Сокращать код за счёт простоты решения, а не плотных однострочников и сложных цепочек выражений.
- Разделять приложение по ответственности; добавлять абстракции и паттерны только для текущей задачи.
- Использовать стандартные средства Swift и macOS, когда они решают задачу напрямую.
- Не добавлять функциональность, настройки и слои «на будущее»; сохранять модульность без лишнего каркаса.
- Поддерживать минималистичный нативный интерфейс в стиле Apple.

# 1. Общая концепция

## 1.1. Назначение

Разработать нативное приложение для macOS, предоставляющее быстрый доступ к возможностям искусственного интеллекта из любой точки операционной системы.

Основной интерфейс — компактное плавающее AI-окно, открываемое глобальным сочетанием клавиш.

Приложение должно позволять пользователю:

1. Задавать произвольные вопросы LLM.
2. Использовать выделенный текст из других приложений.
3. Выполнять заранее настроенные сценарии обработки текста.
4. Создавать собственные сценарии с промптами, моделями и горячими клавишами.
5. Анализировать скриншоты экрана и выбранные области.
6. Вводить запросы голосом.
7. Диктовать текст непосредственно в другие приложения через Push-to-Talk.
8. Преобразовывать распознанную речь с помощью LLM по собственному промпту.
9. Использовать локальные STT-модели без настройки серверов.
10. Скачивать дополнительные STT-модели из встроенного каталога.
11. Сравнивать STT-модели по языкам, размеру, скорости и точности.
12. Подключать локальные и облачные OpenAI-совместимые LLM.

В будущем приложение должно поддерживать AI-агентов, способных использовать инструменты и выполнять разрешённые операции на компьютере.

## 1.2. Принципы продукта

**Нативность**

Приложение разрабатывается на Swift с использованием системных API macOS. Не использовать Electron, WebView в качестве основного UI, Python runtime или отдельный локальный HTTP-сервер.

**Минимализм**

Основные действия доступны через одно плавающее окно. Пользователь не обязан открывать полноценное главное окно для ежедневной работы.

**Локальность**

Распознавание речи выполняется на устройстве. Работа STT не требует интернета или API-ключей.

**Настраиваемость**

Пользователь самостоятельно определяет сценарии, промпты, модели и горячие клавиши.

**Безопасность**

LLM не получает самостоятельный доступ к системным действиям. В MVP все действия с операционной системой выполняются детерминированной логикой приложения.

**Расширяемость**

Архитектура допускает последующее подключение Agent Runtime и системных инструментов без переписывания базового интерфейса.

## 1.3. Разделение режимов

Приложение имеет четыре пользовательских режима:

| Режим | Назначение |
|---|---|
| AI Chat | Произвольные вопросы и диалог с LLM |
| AI Actions | Обработка текста и изображений по сценариям |
| Voice Input | Голосовой ввод запросов внутри AI-панели |
| Push-to-Talk | Диктовка с автоматической вставкой в другие приложения |

Дополнительно существует раздел управления локальными STT-моделями.

В будущих версиях добавляется Agent Mode.

# 5. Первый запуск

## 5.1. Онбординг

При первом запуске пользователь проходит короткую первоначальную настройку.

Шаги:

1. Приветственный экран с кратким описанием приложения.
2. Настройка универсального хоткея.
3. Предоставление необходимых разрешений macOS.
4. Настройка LLM-провайдера, если пользователь хочет использовать AI.
5. Выбор модели LLM.
6. Настройка Push-to-Talk.
7. Проверка локальной диктовки.

Встроенная Whisper Base должна быть доступна сразу после установки.

Указывать STT-провайдера или скачивать дополнительные файлы не требуется.

## 5.2. Работа без LLM

Настройку LLM можно пропустить.

При отсутствии LLM-провайдера должны продолжать работать:

- Локальная диктовка.
- Push-to-Talk без постобработки.
- Менеджер STT-моделей.
- Системные настройки.
- Работа с буфером обмена, не требующая AI.

При попытке запустить AI-запрос отображать предложение подключить LLM.

Приложение не должно блокировать все функции из-за отсутствия LLM.

# 6. Глобальные горячие клавиши

## 6.1. Типы горячих клавиш

Поддержать:

1. Универсальный хоткей открытия AI Palette.
2. Персональные хоткеи пользовательских сценариев.
3. Push-to-Talk.
4. Хоткей захвата экрана или области экрана, если назначен пользователем.

Все сочетания настраиваются через графический интерфейс.

## 6.2. Настройка

Пользователь выбирает поле назначения сочетания и нажимает желаемые клавиши.

Приложение сохраняет:

- Key Code.
- Modifier Flags.
- Назначенное действие.

Не привязывать хоткеи только к текстовому представлению символов.

## 6.3. Конфликты

- Запретить одинаковые сочетания внутри TextCorrect.
- Проверять успешность системной регистрации.
- Не заменять существующее сочетание без подтверждения.
- При конфликте показывать причину.
- После изменения хоткея перерегистрировать его без перезапуска приложения.
- При невозможности использовать комбинацию предложить выбрать другую.

## 6.4. Push-to-Talk

Для Push-to-Talk необходимо отдельно отслеживать начало и завершение удержания.

Не считать событие повторного `keyDown` новой записью.

Запись начинается один раз и завершается при отпускании основной клавиши сочетания.

Обрабатывать случаи потери фокуса, выхода из сна, отзыва разрешений и пропущенного `keyUp`.

Для MVP разрешить сочетания с модификатором и одной обычной клавишей. Использование одиночных системных клавиш, например Fn, без проверки платформенной совместимости не требуется.

# 7. Универсальная AI-панель

## 7.1. Открытие

AI-панель открывается глобальным хоткеем поверх активного приложения.

Перед открытием необходимо попытаться получить текущее выделение и запомнить контекст исходного приложения.

Панель должна быть компактной и не занимать весь экран.

## 7.2. Начальное состояние

Показывать:

- Поле ввода запроса.
- Список доступных сценариев.
- Поле поиска.
- Прикреплённый выделенный текст, если есть.
- Кнопку добавления скриншота.
- Кнопку микрофона.
- Информацию о выбранной LLM.
- Кнопку отправки.

При наличии выделения его необходимо отображать отдельным контекстным блоком.

Пользователь может удалить этот блок до отправки.

## 7.3. Работа без выделения

Если выделенного текста нет:

- AI-панель открывается без ошибки.
- Пользователь может задать произвольный вопрос.
- Доступны сценарии, не требующие выделения.
- Доступно прикрепление изображения.
- Доступен голосовой ввод.

## 7.4. Action Palette

Показывать все созданные сценарии.

Поддерживать:

- Поиск по названию.
- Навигацию стрелками.
- Запуск через Enter.
- Выбор мышью.
- Закрытие через Escape.
- Отображение персонального хоткея.

При открытии первым должен быть выбран первый доступный результат.

Если сценариев нет, показывать предложение создать сценарий.

## 7.5. Позиционирование

Окно размещать в пределах видимой области экрана.

Для MVP использовать центр активного экрана как стандартное положение.

Поддерживать несколько мониторов.

Не допускать открытия панели за пределами экрана.

## 7.6. Состояния UI

Панель должна поддерживать следующие состояния:

- Idle.
- Selecting Action.
- Preparing Context.
- Generating.
- Showing Result.
- Editing.
- Refining.
- Error.

Во время обработки показывать индикатор и кнопку Cancel.

Не отображать выдуманный процент прогресса генерации.

# 8. Пользовательские AI-сценарии

## 8.1. Назначение

Сценарий — сохранённая конфигурация AI-действия.

Примеры:

- Исправить ошибки.
- Сократить текст.
- Перевести на английский.
- Перевести на китайский.
- Переписать в деловом стиле.
- Объяснить выделенный код.
- Составить краткое содержание.

## 8.2. Поля сценария

| Поле | Тип |
|---|---|
| id | UUID |
| name | String |
| description | String? |
| mode | chat / transform |
| system_prompt | String |
| provider_id | UUID |
| model_id | String |
| shortcut | KeyCombination? |
| requires_selection | Bool |
| created_at | Date |
| updated_at | Date |

## 8.3. Управление

Реализовать:

- Создание.
- Редактирование.
- Удаление.
- Дублирование.
- Выбор LLM.
- Назначение хоткея.

Количество сценариев не должно ограничиваться бизнес-логикой приложения.

## 8.4. Стандартные сценарии

После подключения первой LLM можно предложить создать стандартные сценарии:

- Исправить ошибки.
- Сократить текст.
- Перевести текст.
- Улучшить формулировку.

Все стандартные сценарии должны редактироваться и удаляться так же, как пользовательские.

## 8.5. Режимы сценариев

**Chat**

Модель отвечает на вопрос пользователя, используя выделенный текст как контекст.

Например, «Объясни этот код».

**Transform**

Модель преобразует исходный текст в новый.

Например, «Переведи на китайский».

Результат Transform отображается в редактируемом текстовом поле.

# 9. AI-чат

## 9.1. Произвольные запросы

Пользователь может отправить сообщение без выбора сценария.

В качестве контекста использовать прикреплённые материалы текущей сессии.

Если пользователь не прикрепил текст или изображение, запрос выполняется как обычный диалог.

## 9.2. Продолжение диалога

В рамках активной сессии хранить последовательность сообщений.

Каждый следующий запрос передавать с необходимым контекстом предыдущих сообщений.

Не создавать отдельную постоянную историю на диске.

## 9.3. Редактирование ответа

Пользователь должен иметь возможность изменить полученный текст вручную.

В режиме Transform результат является рабочим черновиком.

В режиме Chat сообщение модели остаётся частью истории диалога, но пользователь может открыть его содержимое для редактирования и копирования.

## 9.4. Дополнительные инструкции

Для Transform пользователь может написать:

«Сделай текст короче и менее формальным».

Новый запрос должен включать:

- Системный промпт активного сценария.
- Актуальную рабочую версию текста.
- Дополнительную инструкцию пользователя.

Не отправлять первоначальный текст вместо текущего черновика.

## 9.5. Управление состоянием

Внутри одной сессии разрешается только один активный LLM-запрос.

Повторная отправка во время выполнения не должна создавать дублирующий запрос.

Отмена должна предотвращать применение поздно пришедшего результата.

При ошибке текущий текст и история успешных сообщений сохраняются.

# 10. Работа с выделенным текстом

## 10.1. Получение выделения

Использовать macOS Accessibility API.

Сохранять:

- Идентификатор приложения.
- Ссылку на редактируемый элемент, если доступна.
- Исходное выделение.
- Диапазон выделения.
- Информацию для проверки актуальности.
- Способ получения выделения.

## 10.2. Резервный механизм

Если Accessibility не предоставляет выделенный текст, допускается резервный механизм копирования.

Требования:

- Не отправлять пустое выделение.
- По возможности сохранять содержимое буфера обмена.
- Не перезаписывать изменения буфера, внесённые пользователем во время операции.
- Не выполнять небезопасную вставку при потере контекста.
- Не читать защищённые поля.

## 10.3. Замена текста

В AI-панели **запрещена автоматическая замена**.

Результат можно:

- Скопировать.
- Изменить вручную.
- Дополнительно обработать.
- Заменить в исходном приложении отдельной кнопкой.

## 10.4. Безопасность замены

Перед заменой:

1. Проверить существование исходного приложения.
2. Проверить исходный элемент.
3. Проверить доступность диапазона.
4. Проверить актуальность исходного текста.
5. Убедиться, что операция не изменит другое поле.
6. Выполнить замену поддерживаемым механизмом.

Если безопасная замена невозможна, запретить операцию и предложить Copy.

Нельзя вставлять текст в произвольное текущее поле только потому, что исходное поле стало недоступным.

## 10.5. Форматирование

Сохранять структуру документа и оформление по возможности.

Сохранение сложного rich text не гарантируется.

Нельзя изменять содержимое вне исходного выделения.

Для неподдерживаемых редакторов допускается режим только копирования.

# 11. Редактор результатов

## 11.1. Интерфейс

После ответа LLM отображать:

- Результат.
- Многострочный редактор.
- Поле дополнительной инструкции.
- Copy.
- Replace Original, когда применимо.
- Cancel во время генерации.
- Close.

## 11.2. Поведение

Текст результата должен быть доступен для обычного редактирования.

Поддерживать:

- Выделение.
- Вставку.
- Удаление.
- Переносы строк.
- Unicode.
- Большие тексты.
- Прокрутку.

## 11.3. Повторная генерация

При отправке инструкции:

1. Зафиксировать текущую версию текста.
2. Отправить её LLM.
3. Заблокировать конкурирующее редактирование на время запроса.
4. При успехе показать новый текст.
5. При ошибке сохранить предыдущий.

Не добавлять обязательный просмотр diff в MVP.

## 11.4. Закрытие

При обычном скрытии окна текущая сессия может сохраняться в оперативной памяти до явного завершения или создания новой сессии.

При явном закрытии сессии её содержимое удаляется из оперативного состояния.

Если пользователь пытается уничтожить сессию с несохранёнными ручными правками, показывать предупреждение.

# 12. LLM-провайдеры

## 12.1. Поддерживаемый протокол

В MVP поддерживаются OpenAI-совместимые HTTP API.

Основной endpoint:

`POST /chat/completions`

Для моделей:

`GET /models`

Пользователь указывает полный API Base URL, например `http://localhost:1234/v1`.

Приложение должно корректно добавлять путь endpoint, не дублируя `/v1`.

## 12.2. Настройки провайдера

| Поле | Описание |
|---|---|
| id | UUID |
| name | Название подключения |
| base_url | Корень API |
| api_key | Ссылка на запись Keychain |
| models | Список моделей |
| created_at | Дата создания |

## 12.3. Настройка моделей

Поддерживать:

- Получение списка через API.
- Ручной ввод Model ID.
- Выбор модели.
- Проверку соединения.
- Ручную настройку поддержки изображений.

Если провайдер не реализует `/models`, ручной Model ID должен оставаться работоспособным.

## 12.4. Совместимые системы

Предусмотреть работу с:

- LM Studio.
- Ollama через OpenAI-совместимый endpoint.
- OpenAI-совместимыми облачными API.
- Пользовательскими совместимыми серверами.

Не реализовывать отдельные нестандартные API без необходимости.

## 12.5. Генерация

Использовать стандартные сообщения:

- system.
- user.
- assistant.

Для Transform текущий текст передавать явно, отдельно от инструкции пользователя.

Не допускать ситуации, при которой предыдущее редактирование теряется из-за некорректного контекста.

## 12.6. Мультимодальность

Для изображений использовать поддерживаемый провайдером формат Chat Completions.

При отсутствии поддержки изображений:

- Не отправлять некорректный запрос.
- Предложить сменить модель.
- Сохранить прикреплённый скриншот в сессии.

## 12.7. Ошибки и таймауты

Таймаут по умолчанию — 120 секунд.

Допустить пользовательскую настройку в диапазоне 30–300 секунд.

Обрабатывать:

- Ошибки соединения.
- Таймаут.
- HTTP 401/403.
- HTTP 404.
- HTTP 429.
- HTTP 5xx.
- Некорректный JSON.
- Пустой ответ.
- Отсутствующую модель.
- Несовместимый формат ответа.
- Превышение контекстного окна.

Автоматически повторять запросы не нужно.

Обязательно поддерживать отмену.

Потоковая выдача ответа желательна, но для MVP допустимо отображение полного результата после завершения запроса.

# 13. Скриншоты

## 13.1. Функции

Пользователь может:

- Сделать снимок всего экрана.
- Выбрать область.
- Прикрепить изображение к запросу.
- Просмотреть миниатюру.
- Удалить изображение до отправки.

## 13.2. Выделение области

По команде Capture Region:

1. Активировать режим захвата.
2. Дать пользователю выделить прямоугольную область.
3. Получить изображение указанной области.
4. Добавить его в текущую AI-сессию.
5. Вернуть пользователя к AI-панели.

Отмена выбора не должна создавать пустое изображение.

## 13.3. Системная реализация

Использовать ScreenCaptureKit и нативный механизм выбора содержимого или собственную overlay-область при необходимости.

Правильно учитывать:

- Retina scaling.
- Несколько мониторов.
- Разные размеры экранов.
- Различные системы координат.
- Видимую область рабочего стола.

Не включать собственное всплывающее окно TextCorrect в снимок, если пользователь захватывает изображение для анализа другого приложения.

## 13.4. Отправка

Перед отправкой проверить, что выбранная LLM поддерживает изображения.

Изображение не должно автоматически отправляться только по факту захвата.

В MVP достаточно одной или нескольких картинок в рамках одного запроса, если это поддерживает выбранный API.

Файлы изображений не сохраняются постоянно.

# 14. Голосовой ввод в AI-панели

## 14.1. Интерфейс

В поле ввода должна находиться кнопка микрофона.

Сценарий:

1. Пользователь запускает запись.
2. Произносит запрос.
3. Останавливает запись.
4. Приложение выполняет STT.
5. Распознанный текст появляется в поле ввода.
6. Пользователь может исправить его.
7. Пользователь отправляет запрос LLM.

Распознавание не должно автоматически отправлять сообщение.

## 14.2. Использование модели

Использовать выбранную локальную STT-модель из общего Speech Model Manager.

Не требовать отдельной настройки STT для AI-панели.

# 15. Push-to-Talk

## 15.1. Назначение

Реализовать глобальную диктовку в любое поддерживаемое редактируемое поле macOS.

## 15.2. Сценарий

1. Пользователь устанавливает курсор в текстовое поле.
2. Удерживает назначенный хоткей.
3. Начинается запись микрофона.
4. Пользователь диктует.
5. Отпускает сочетание клавиш.
6. Запись прекращается.
7. Выбранная локальная STT-модель распознаёт речь.
8. При необходимости запускается LLM-постобработка.
9. Готовый текст вставляется в исходное поле.

## 15.3. Интерфейс

Во время диктовки показывать компактный ненавязчивый индикатор.

Состояния:

- Recording.
- Transcribing.
- Postprocessing.
- Inserting.
- Completed.
- Error.

Показывать возможность отмены операции.

Основное AI-окно не открывать.

## 15.4. Продолжительность записи

Поддерживать короткие и длинные диктовки.

Для MVP:

- Минимальная полезная запись определяется наличием распознанной речи.
- Максимальная длительность одной записи — 10 минут.
- При достижении ограничения автоматически остановить запись и начать обработку.
- Длительные записи обрабатывать порциями, если этого требует STT-движок.

Не хранить всю длинную запись в одном неограниченно растущем буфере памяти.

## 15.5. Защита от ошибок

Не вставлять текст, если:

- Исходное поле исчезло.
- Исходное приложение закрыто.
- Курсор перемещён в другое поле.
- Положение вставки невозможно надёжно восстановить.
- Пользователь отменил операцию.
- Результат пустой.

При невозможности вставки показывать компактное окно с текстом и кнопкой Copy.

# 16. LLM-постобработка диктовки

## 16.1. Назначение

После STT пользователь может дополнительно преобразовать распознанный текст через LLM.

Постобработка должна быть полностью опциональной.

## 16.2. Настройки

В разделе Voice Input реализовать:

- Переключатель Enable LLM Postprocessing.
- Выбор LLM-провайдера.
- Выбор модели.
- Многострочный редактор промпта.
- Сохранение настроек.
- Возможность тестового запуска.

## 16.3. Алгоритм

**Если постобработка выключена:**

`Audio → STT → Text Insertion`

**Если постобработка включена:**

`Audio → STT → LLM → Text Insertion`

Результат LLM является окончательным текстом для вставки.

## 16.4. Поведение модели

Полностью определяется пользовательским промптом.

Возможные применения:

- Исправление грамматики.
- Исправление пунктуации.
- Сохранение разговорного стиля.
- Удаление слов-паразитов.
- Преобразование в деловой стиль.
- Перевод.
- Структурирование.
- Обработка технических терминов.
- Преобразование диктовки в задачу.

Не добавлять жёстко заданные правила стилистической обработки поверх промпта пользователя.

## 16.5. Ошибки

Если STT сработал, но LLM вернула ошибку:

- Сохранить исходную расшифровку.
- Не вставлять ошибочный или пустой результат.
- Показать пользователю доступный STT-текст.
- Предложить вставить его без постобработки или скопировать.

Не выполнять автоматический fallback с незаметной вставкой исходной расшифровки вместо LLM-результата.

# 17. Встроенный локальный STT

## 17.1. Основное требование

TextCorrect должен иметь готовое локальное распознавание речи сразу после установки.

Пользователь не должен:

- Создавать STT API Key.
- Выбирать STT-провайдера.
- Запускать локальный сервер.
- Устанавливать Python.
- Настраивать отдельный inference engine.
- Скачивать обязательные компоненты для первой диктовки.

## 17.2. Встроенная модель

**Whisper Base Multilingual**.

Технические параметры:

| Параметр | Значение |
|---|---|
| Модель | Whisper Base |
| Формат | GGML |
| Файл | `ggml-base.bin` |
| Примерный размер | 148 МБ |
| Движок | whisper.cpp |
| Инференс | Локальный |
| Языки | Многоязычная модель, включая русский |
| Загрузка | Встроена в установочный пакет |
| Интернет | Не нужен |

Использовать именно мультиязычную версию `base`, а не `base.en`.

## 17.3. Инференс

Интегрировать whisper.cpp непосредственно в приложение.

Предусмотреть использование аппаратных возможностей Apple Silicon, включая Metal.

Дополнительное ускорение Core ML допускается при наличии подготовленных совместимых ресурсов.

Основной STT должен работать без отдельного Python-процесса.

## 17.4. Аудиоданные

Запись выполнять через AVAudioEngine.

Перед инференсом:

- Приводить аудио к формату, поддерживаемому движком.
- Обрабатывать sample rate.
- Преобразовывать многоканальный сигнал при необходимости.
- Избегать лишнего накопления аудио в памяти.

Для Whisper использовать поддерживаемый PCM-формат и частоту дискретизации, требуемую конкретной реализацией.

## 17.5. Жизненный цикл модели

- Не загружать модель в память без необходимости.
- Загружать при первом запуске STT.
- Допускать кеширование загруженной модели между короткими сессиями.
- Выгружать модель после длительного простоя.
- Не загружать одновременно несколько тяжёлых STT-моделей без необходимости.

- Not Installed.
- Downloading.
- Verifying.
- Installing.

## 18.7. Установка

Алгоритм:

1. Получить запись модели из каталога.
2. Проверить совместимость с текущим приложением.
3. Проверить доступное место на диске.
4. Скачать необходимые файлы во временную папку.
5. Проверить контрольные суммы.
6. Проверить формат и комплектность.
7. Атомарно переместить в каталог установленных моделей.
8. Обновить состояние модели.
9. Сделать её доступной для выбора.

При повреждении загрузки не считать модель установленной.

## 18.8. Удаление

Удалять можно только скачанные модели.

Перед удалением активной модели необходимо переключиться на другую установленную модель.

Запретить удаление модели во время её использования.

Если пользователь удаляет все дополнительные модели, Whisper Base остаётся доступной.

## 18.9. Хранение

Встроенная модель находится внутри `.app`.

Дополнительные модели хранить по пути:

`~/Library/Application Support/TextCorrect/Models/`

Использовать отдельную директорию для каждой модели и версии.

Не смешивать скачанные веса с исполняемыми компонентами приложения.

## 18.10. Offline-режим

При отсутствии интернета:

- Установленные модели доступны.
- Встроенная Whisper Base доступна.
- Активная модель не сбрасывается.
- Каталог показывает кешированные данные.
- Новые загрузки недоступны с соответствующим сообщением.

# 19. Фильтрация STT-моделей

## 19.1. Фильтр по языку

Добавить выпадающий список языков.

- Все языки.
- Русский.
- Английский.
- Китайский.

Список формировать из метаданных моделей.

## 19.2. Логика фильтрации

# 21. Точность и скорость STT-моделей

## 21.1. Отображение

В карточке модели показывать две горизонтальные шкалы:

**Accuracy** — точность распознавания.

**Speed** — производительность.

Шкалы предназначены для визуального сравнения, а не настройки параметров.

Если проверенных данных нет, отображать «Нет данных».

## 21.2. Точность

Для оценки использовать WER (Word Error Rate).

Чем ниже WER, тем качественнее распознавание на соответствующем тестовом наборе.

Хранить:

- Значение WER.
- Язык.
- Датасет.
- Версию датасета.
- Метод нормализации.
- Источник.
- Дату тестирования.
- Версию модели.

## 21.3. Язык и точность

Точность должна зависеть от выбранного языка.

Например, при выборе русского показывать результат русского бенчмарка.

Не использовать результат английского бенчмарка как оценку точности русского распознавания.

Если русского теста нет, показывать «Нет данных».

## 21.4. Скорость

Использовать показатель Real-Time Factor.

Предпочтительно хранить:

- RTF.
- RTFx.
- Модель Mac.
- Чип.
- Объём памяти.
- Inference Engine.
- Backend.
- Длительность тестового аудио.
- Версию модели.
- Дату измерения.

RTFx показывает, во сколько раз быстрее реального времени выполняется распознавание.

Например, `5x` означает обработку 60 секунд аудио приблизительно за 12 секунд в указанных условиях.

## 21.5. Сопоставимость

Не сравнивать напрямую измерения, выполненные:

- На разных процессорах.
- На разных датасетах.
- С разными методами подсчёта.
- С разными настройками инференса.

Нормализованные шкалы рассчитывать только для сопоставимых результатов.

В подписи показывать реальные значения WER и RTFx, а не только заполнение полоски.

## 21.6. Источники бенчмарков

Приоритет:

1. Собственные воспроизводимые тесты TextCorrect.
2. Опубликованные результаты с известной методикой.
3. «Нет данных», если сопоставимых измерений нет.

Для собственных тестов использовать фиксированный воспроизводимый набор аудио.

В документации бенчмарков зафиксировать:

- Версию корпуса.
- Лицензию корпуса.
- Язык.
- Длительности записей.
- Методику нормализации.
- Оборудование.
- Версию runtime.

## 21.7. Визуальные шкалы

Заполнение шкал должно быть вычисляемым и воспроизводимым.

Разрешается использовать нормализованные сравнительные оценки внутри одной группы бенчмарков.

Обязательно хранить метод расчёта и показывать исходное измерение.

Нельзя выдавать заполнение шкалы за объективную вероятность правильного распознавания.

При отсутствии данных шкала остаётся незаполненной с подписью «Нет данных».

# 22. Формат каталога моделей

## 22.1. Источник каталога

Использовать версионированный JSON-манифест в GitHub-репозитории проекта.

Приложение должно содержать резервную локальную копию каталога.

## 22.2. Структура

Каждая модель должна содержать:

| Поле | Назначение |
|---|---|
| id | Уникальный идентификатор |
| name | Название |
| description | Описание |
| engine | Требуемый runtime |
| engine_version | Совместимая версия |
| format | Формат весов |
| languages | Список ISO-кодов языков |
| bundled | Встроенная ли модель |
| download_size | Размер загрузки |
| installed_size | Ожидаемый размер на диске |
| source_repository | Репозиторий весов |
| source_revision | Закреплённая ревизия |
| files | Список необходимых файлов |
| checksums | Контрольные суммы SHA-256 |
| license | Лицензия |
| min_macos | Минимальная версия macOS |
| benchmarks | Доступные измерения |
| catalog_version | Версия метаданных |

## 22.3. Обновление каталога

Каталог может обновляться независимо от приложения.

При обновлении:

- Проверять версию схемы.
- Проверять совместимость с установленными inference engines.
- Игнорировать неподдерживаемые модели.
- Сохранять предыдущую рабочую версию каталога при ошибке.
- Не удалять уже установленные модели автоматически.

## 22.4. Безопасность загрузок

- Использовать HTTPS.
- Загружать только из разрешённых проверенных источников.
- Закреплять ревизии весов.
- Проверять SHA-256.
- Не запускать скачанный исполняемый код.
- Защищаться от некорректных путей и повреждённых архивов.
- Проверять лицензии перед включением модели в публичный каталог.

Для Hugging Face использовать закреплённые версии файлов, а не полагаться на изменяемую ветку `main` при проверке целостности.

# 24. Будущая поддержка AI-агентов

## 24.1. Назначение

В будущих версиях пользователь сможет включать Agent Mode.

Агент сможет выполнять задачи, используя инструменты.

Примеры:

- Искать информацию в интернете.
- Читать веб-страницы.
- Анализировать разрешённые файлы.
- Создавать и изменять документы.
- Выполнять разрешённые команды.
- Взаимодействовать с приложениями macOS.
- Выполнять последовательные действия.

## 24.2. Архитектура

Предусмотреть возможность подключения отдельного:

`AgentEngine`

Он должен использовать существующий интерфейс `InteractionEngine`.

Будущий Agent Runtime будет включать:

- Tool Calling.
- Tool Registry.
- Tool Executor.
- Permission Layer.
- Task State.
- Execution Limits.
- User Confirmation.

## 24.3. Безопасность

Агент не должен автоматически получать полный доступ к устройству.

В будущем предусмотреть:

- Разрешение конкретных инструментов.
- Подтверждение системных действий.
- Отдельные разрешения на чтение и запись.
- Ограничения сетевого доступа.
- Ограничения выполнения команд.
- Изоляцию инструментов.
- Логирование действий агента с исключением секретов.

Содержимое файлов и веб-страниц считать недоверенными данными, а не системными инструкциями.

## 24.4. Изоляция

Для выполнения системных команд рассмотреть отдельный helper-процесс или другой изолированный исполнитель.

Agent Runtime не должен исполнять произвольный shell-код внутри основного UI-процесса.

Конкретную модель изоляции выбрать при реализации Agent Mode.

## 24.5. Ограничения MVP

В первой версии:

- Нет Agent Mode в интерфейсе.
- Нет Tool Calling.
- Нет Tool Registry.
- Нет выполнения AI-команд.
- Нет самостоятельного доступа модели к файловой системе.

Требуется только сохранить архитектурную возможность расширения.

# 26. Управление конкурентностью

## 26.1. LLM

В рамках одной AI-сессии только один активный запрос.

Новая инструкция не запускается до завершения или отмены предыдущей.

## 26.2. STT

Не допускать одновременного запуска двух диктовок через один микрофон.

Повторное нажатие Push-to-Talk во время обработки не должно создавать вторую запись.

## 26.3. Загрузка моделей

Разрешить фоновое скачивание моделей независимо от основного UI.

При удалении активной модели запрещать операцию до её выгрузки.

## 26.4. Отмена

Все длительные операции должны поддерживать отмену там, где это технически возможно.

После отмены:

- Не применять поздние ответы.
- Не вставлять текст.
- Освобождать временные ресурсы.
- Не оставлять интерфейс в состоянии бесконечной загрузки.

# 27. Безопасность и конфиденциальность

## 27.1. Данные пользователя

- Не собирать телеметрию.
- Не сохранять тексты запросов в логах.
- Не хранить историю диктовок.
- Не отправлять STT-аудио в сеть.
- Не отправлять скриншоты без явного действия.
- Не передавать данные другим LLM-провайдерам.
- Не читать защищённые поля.
- Не записывать нажатия клавиатуры вне обработки настроенных хоткеев.

## 27.2. Облачные модели

Перед первой отправкой пользовательского содержимого облачной LLM сообщить, что данные будут переданы выбранному провайдеру.

Для локальных подключений такое предупреждение о внешней передаче не требуется, но интерфейс должен показывать адрес подключения.

## 27.3. Системные разрешения

Управлять разрешениями:

- Accessibility.
- Microphone.
- Screen Recording.
- Input Monitoring, если требуется для реализации хоткеев.
- Другие разрешения, необходимые конкретным API.

Не запрашивать все разрешения без необходимости.

При отказе показывать инструкцию и сохранять доступность остальных функций.

## 27.4. Модель безопасности агента

Будущие агентные возможности не должны ослаблять ограничения обычных LLM-сценариев.

Никакой текст ответа LLM не должен автоматически интерпретироваться как системная команда.

Создать воспроизводимый тестовый набор для оценки моделей.

Минимально включить русский и английский языки.

Использовать фиксированные аудиозаписи с эталонными транскрипциями.

Методика должна позволять сравнить разные STT-модели по единому протоколу.

Отдельно измерять:

- Время загрузки модели.
- Время распознавания.
- WER.
- Пиковое потребление памяти.

Результаты хранить отдельно от пользовательских данных.

# 34. Итоговое Definition of Done

Разработка считается завершённой после выполнения всех обязательных требований, прохождения тестов и подготовки публичной сборки.

Приложение должно позволять пользователю выполнить следующие сценарии.

**Сценарий A — вопрос к AI**

Нажать глобальный хоткей, написать вопрос и получить ответ, не открывая браузер.

**Сценарий B — исправление текста**

Выделить текст в Telegram, открыть AI-панель, выбрать «Исправить ошибки», получить результат, при необходимости дополнительно его изменить и заменить исходное выделение вручную.

**Сценарий C — собственный сценарий**

Создать профиль с собственным промптом, моделью и горячей клавишей. Запускать его из любого поддерживаемого приложения.

**Сценарий D — анализ изображения**

Выделить область экрана с ошибкой, добавить снимок в AI-запрос и получить объяснение от мультимодальной LLM.

**Сценарий E — голосовой вопрос**

Открыть AI-панель, продиктовать запрос, отредактировать распознанный текст и отправить LLM.

**Сценарий F — глобальная диктовка**

Установить курсор в редактор, удерживать Push-to-Talk, произнести текст и отпустить клавиши. Получить локальную расшифровку и безопасную автоматическую вставку.

**Сценарий G — постобработка диктовки**

Включить LLM-постобработку, написать собственный промпт и получать автоматически преобразованный результат голосового ввода.

**Сценарий H — установка другой STT-модели**

Открыть Speech Models, выбрать русский язык, отсортировать модели по размеру, изучить доступные показатели точности и скорости, скачать модель и назначить её активной.

**Сценарий I — полностью локальное STT**

Отключить интернет и продолжать пользоваться Whisper Base для распознавания и вставки речи без LLM-постобработки.

**Сценарий J — безопасная ошибка**

Начать диктовку или AI-обработку, затем изменить или закрыть исходное поле. Приложение не должно вставлять текст в другое место или терять готовый результат.

# 35. Основной архитектурный результат

TextCorrect должен состоять из независимых систем:

1. **Native macOS UI** — окна, Menu Bar и горячие клавиши.
2. **Context System** — выделенный текст и скриншоты.
3. **LLM System** — провайдеры, сценарии, чат и обработка.
4. **Speech System** — запись аудио, STT и локальные модели.
5. **Text Insertion System** — безопасная вставка и замена.
6. **Configuration System** — настройки, профили и секреты.
7. **Future Agent Integration** — архитектурная точка подключения агента.

В MVP все действия предсказуемы и управляются приложением.

**Главный критерий качества:** TextCorrect предоставляет удобный, быстрый и безопасный доступ к AI из любого поддерживаемого приложения macOS, включая текстовые запросы, пользовательские сценарии, визуальный контекст и локальный голосовой ввод.

Архитектура должна оставаться достаточно простой для поддержки и при этом позволять в будущем добавить полноценного AI-агента без переписывания основных компонентов.
